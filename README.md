# Аналітичний асистент для райд-хейлінгу

Тестове завдання Data Scientist (Middle).

**Демо:** https://ride-hailing-analytics.fly.dev/

Синтетичний маркетплейс Києва на **60 днів**: попит, вільні водії, динамічний
коефіцієнт і ETA кожні 15 хвилин + воронка від розрахунку ціни до прийняття /
відтоку. Асистент відповідає природною мовою, пише SQL і будує графіки.

Чому не відкритий датасет таксі: у публічних логах майже завжди лише *виконані*
поїздки — немає тих, хто подивився ціну й пішов, немає пулу вільних водіїв і
окремого коефіцієнта. Без цього воронку брифу не порахувати, тому дані
згенеровані (`configs/` + фіксований seed).

## Що всередині

| Частина | Суть |
|---|---|
| Датасет | PostgreSQL: `rides` (~737k), `zone_state` (зона × 15 хв), 20 зон Києва |
| Контекст | комендантська 00:00–05:00, повітряні тривоги, погода, піки |
| Воронка | calculated → placed → accepted **або** churned_to_competitor |
| Асистент | LangChain/LangGraph + Claude (OpenRouter), аналітичні інструменти + `run_sql` |
| Акцент DS | баланс попит/пропозиція; парадокс Сімпсона (surge vs acceptance при контролі ETA) |

## Логіка ринку

**Ціна й ETA реагують не на обсяг попиту, а на дефіцит водіїв**
(`demand / available_drivers`). На Хрещатику о 13:00 попит помірний (~14), але
коефіцієнт ≈1.31 — водіїв менше через обідню паузу; о 08:00 при близькому попиті
водіїв більше (~17) → коефіцієнт ≈1.12.

## Воронка і метрики

```
розрахунок ціни  →  замовлення (placed)  →  пошук (~2–5 хв)
                                      ├─→ accepted
                                      └─→ churned_to_competitor
```

| Зріз (seed 42) | Значення |
|---|---|
| Розрахунків | 736 803 |
| Placed | 462 997 (62.8%) |
| Accepted | 396 837 (85.7% of placed) |
| Churn | 66 160 (14.3% of placed) |
| ETA ≤ 10 хв серед accepted | ~91% |

| Метрика | Формула | Знаменник |
|---|---|---|
| place conversion | `placed / calculated` | усі розрахунки |
| acceptance rate | `accepted / placed` | лише placed |
| competitor churn | `churned_to_competitor / placed` | лише placed |
| end-to-end | `accepted / calculated` | усі розрахунки |
| supply gap | `demand_count − available_drivers` | зона × інтервал |

Churn — proxy реального сценарію «довго немає машини → конкурент / повзунок ціни»
(повзунок окремо не моделювали).

## На що дивитися в захисті

- **Обід vs ранок (Хрещатик)** — помірний попит о 13:00 дає вищий коефіцієнт,
  ніж зранку, бо менше вільних водіїв → важливий ratio, не «пікова година»
- **Surge і acceptance** — маргінально коефіцієнт може виглядати «шкідливим»; при
  фіксованому ETA acceptance з ним росте (Сімпсон / confounding через ETA)
- **Комендантська** — обвал обсягу (~4% попиту), не «тиха ніч»
- **Тривоги** — модельна гіпотеза: попит майже тримається (substitution з ОТ),
  доступна пропозиція падає сильніше → знову сплеск коефіцієнта

## Швидкий старт (локально)

Потрібні Python 3.11, Docker і ключ [OpenRouter](https://openrouter.ai)
(лише для чату; REST-аналітика працює без ключа).

```bash
make install && cp .env.example .env   # вписати OPENROUTER_API_KEY
make db-up && make reset && make serve
```

Відкрити http://localhost:8000 · `make help` — усі команди ·
`make validate` — 38 інваріантів на даних · `make test` — pytest.
